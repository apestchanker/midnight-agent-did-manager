- **Column placement in SQL statements**: For both the insert and update branches of `createOrUpdateDidRequestRecord`, the new `controller` column/param was appended at the very end of the existing column list and params array (rather than interleaved next to `subject_wallet_address`). This kept every existing 0-indexed `params[N]` assertion in `tests/registry-service-request.test.ts` (e.g. `params[3]`, `params[6]`, `params[11]`) unchanged, minimizing the diff and avoiding an unrelated ripple through untouched test assertions. Task 5's `upsertIssuedDidRecord` (insert `$16`, update `$11`) and `syncWalletUpdatedDid` (`$5`) follow the same trailing-append convention for consistency.
- **Test file for MCP-flow controller assertion**: Deviated from `tasks.json`'s listed file (`tests/registry-service-mcp.test.ts`) and instead extended `tests/registry-service-request.test.ts`, which is where the actual `createDidRequest` (MCP flow) test already lives. `tests/registry-service-mcp.test.ts` covers a different concern (MCP key/scope CRUD) and has no `createDidRequest` coverage at all. This should be reflected back into `tasks.json`'s `files` array for task 3 if the spec is revised later (informational only — not corrected in tasks.json itself, since the task planner's file list is treated as a hint, not a hard contract, per the sdd-implementer's mandate to use the project's actual existing test pattern).
- **RED verification method**: Used `git stash push -- server/registry-service.js` to temporarily isolate and revert only the task-3 implementation diff (leaving tasks 1/2's type and schema changes in place, which are inert w.r.t. these tests), ran the target test file to confirm the 3 new/extended assertions fail with implementation-absent diagnostics, then `git stash pop` to restore. This was necessary because the implementation was written in the same pass as the tests (to keep the edit sequence coherent); the stash round-trip is a faithful substitute for writing tests strictly before any implementation edit. Tasks 4 and 5 instead wrote the new test cases first, ran the suite unmodified (implementation not yet touched) to observe genuine RED, and only then edited `server/registry-service.js`/`request-document.js` — no stash round-trip was needed since tests were authored strictly before the implementation edit in this batch.
- **`upsertIssuedDidRecord`'s update branch uses a plain overwrite (`controller = $11`), not `coalesce`**: Per the technical spec, `coalesce` is a hard requirement only for `syncWalletUpdatedDid` (an update call whose caller may legitimately omit `controller` and expects the existing value preserved). `upsertIssuedDidRecord`'s two callers (`issueApprovedDidRequest`, `syncWalletIssuedDid`) always pass an already-resolved definitive `controller` value (from the persisted request row or from the sync payload respectively) at issuance time, so a plain overwrite matches the spec's literal wording ("`controller = $N`", no coalesce mentioned) and does not risk nulling out data in practice, since both call sites already resolved their own fallback before calling in.
- **Coalesce risk coverage in a mocked-DB test environment**: Since this repo has no real-Postgres test harness (all `registry-service.js` tests mock `server/db.js`), the coalesce risk (task 5's #1 identified risk) is verified structurally — asserting the emitted SQL text matches `controller = coalesce($N, controller)` and that the bound parameter is `null` when the caller omits `controller` — rather than by observing actual Postgres coalesce semantics. This mirrors the same mocked-DB testing pattern already used throughout this codebase's `registry-service.js` test suite (see `sdd/wip/006-.../meta.md` Notes on test-infra gaps).

- **`updateDid`/`issueDid` conditional-patch fallback pattern**: The technical spec's literal `Component Design` wording ("include it in mergeDidMetadata(...) patch ... controller: opts.controller ?? cached.controller") doesn't spell out whether the patch inclusion should be unconditional. Read together with the tasks.json acceptance criterion ("falls back to the cached value when omitted"), unconditional inclusion would break the fallback (mergeDidMetadata's `{...existing, ...patch}` spread overwrites even with an `undefined` patch value), so `updateDid`/`issueDid` use a conditional spread while `gatedSelfRegisterDid` (whose acceptance criteria don't require a cached-fallback) keeps the simpler unconditional form matching its sibling `subjectWalletAddress` field in the same function. This is a deliberate, test-driven interpretation choice, not an ambiguity left unresolved.
- **`tests/service-api.test.ts` RED was a no-op at that file's own test level**: Because `tsconfig.json`'s `include` excludes `tests/`, and vitest's esbuild transform strips types without enforcing them, object literals with extra properties (like a `controller` field not yet declared on a payload type) pass straight through to `JSON.stringify` and are visible in the request body regardless of whether the source type declares them. The real type-safety enforcement point for task 7's `serviceApi.ts` changes is `app-api.ts` (a `tsconfig.json`-included file) failing to compile if it passes `controller` to a payload type that doesn't declare it — confirmed clean via `npx tsc --noEmit` only after both files were updated together.

- **Tasks 8/9 testing approach — pure-logic extraction over adding jsdom/@testing-library/react**: Chosen per explicit orchestrator instruction and `meta.md`'s pre-flagged gap. `vitest.config.ts` sets no `test.environment` (defaults to `"node"`, confirmed by inspection — no `jsdom`/`happy-dom` dependency in `package.json` either), so no component could actually be rendered without first adding that infrastructure from scratch, which would be new-pattern surface area for a two-component styling/state change. Both components' "logic that matters" (default-population source-of-truth chains, and state-field independence) turned out to be cleanly separable from JSX: `src/lib/did/request-form-state.ts` (task 8) and `src/lib/did/issuer-panel-state.ts` (task 9), each a plain `.ts` module with no React import, tested via ordinary `vitest` `describe`/`it` — same style as every other test file in this repo (e.g. `tests/did-request-document.test.ts`). Both modules are then imported and actually used by their respective `.tsx` component (not just written as an unused parallel implementation) — `RequestForm.tsx` now uses `useReducer(agentControllerReducer, ...)` instead of two independent `useState` calls specifically so the state-independence tests exercise the exact reducer the component dispatches into at runtime, not a structural proxy for it.
